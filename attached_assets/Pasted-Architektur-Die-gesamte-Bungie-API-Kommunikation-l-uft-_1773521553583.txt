Architektur
Die gesamte Bungie-API-Kommunikation läuft über einen einzigen Express-Server, der gleichzeitig das Frontend served. Wenn ein Manifest-Fetch hängt oder ein langsamer Bungie-Call blockiert, betrifft das alle User. Eine Trennung in API-Server und Static-Serving (oder zumindest ein Worker-Thread für Manifest-Downloads) würde die Stabilität erhöhen.
Die storage.ts hat ein IStorage-Interface, aber es gibt nur eine Implementierung (DatabaseStorage). Das Interface ist trotzdem gut — allerdings fehlt eine In-Memory-Implementierung für lokales Development ohne Datenbank. Das würde das Onboarding neuer Entwickler vereinfachen.
routes.ts ist mit 615 Zeilen eine Gott-Datei. Die Bungie-Proxy-Routen, Auth-Routen, Loadout-CRUD und AI-Endpunkte könnten in separate Router-Module aufgeteilt werden. Gleiche Situation bei bungie.ts mit 1484 Zeilen — das Manifest-Handling, die Profile-Parsing-Logik und die Action-Funktionen (Transfer, Equip etc.) sind drei klar trennbare Module.
Datenfluss
Der Client pollt nie automatisch nach neuen Profildaten. staleTime ist auf 2 Minuten gesetzt, aber refetchInterval ist false. Wenn ein User 10 Minuten auf dem Dashboard sitzt und jemand ihm in-game Items schickt, sieht er das erst nach manuellem Refresh. Ein sanfter Refetch alle 5 Minuten (oder ein WebSocket für Push-Updates) wäre nutzerfreundlicher.
Nach jeder Mutation (transferItem, equipItem etc.) wird invalidateQueries auf den gesamten Profile-State aufgerufen. Das triggert einen kompletten Re-Fetch aller Profildaten von Bungie — Characters, Vault, Collectibles, Records, alles. Für einen simplen Item-Transfer ist das massiv überdimensioniert. Optimistic Updates auf Client-Seite (Item aus Vault entfernen, zum Charakter hinzufügen) mit einem verzögerten Hintergrund-Refresh wären wesentlich performanter.
Edge Cases
Wenn ein User mehrere Browser-Tabs offen hat und in Tab A ein Item transferiert, weiß Tab B nichts davon. Der nächste Transfer in Tab B könnte fehlschlagen, weil das Item nicht mehr dort ist wo erwartet. Ein BroadcastChannel oder SharedWorker könnte Tabs synchron halten.
Der nanoid(32) für Session-IDs ist kryptographisch ausreichend, aber der nanoid(10) für Share-Codes ist mit ~10^17 Möglichkeiten etwas knapp bei hoher Nutzerzahl. Kein akutes Problem, aber bei Wachstum könnte eine Collision-Check-Logik sinnvoll sein — du hast unique() auf der DB-Spalte, aber der Fehlerfall wird nicht abgefangen.
Beim Loadout-Speichern wird items als jsonb gespeichert. Wenn sich das Item-Schema ändert (z.B. neue Felder), werden alte Loadouts mit dem alten Schema geladen. Es fehlt eine Versionierung der Loadout-Daten oder zumindest eine Migration-Strategie.
Client-Qualität
framer-motion wird in fast jeder Komponente importiert. Das ist eine ~30kb Library (gzipped). Viele Animationen (fade-in, slide) könnten mit CSS-Transitions oder der nativen Web Animations API erreicht werden. Für die komplexeren Animationen (AnimatePresence, layout-Animationen) ist framer-motion berechtigt, aber für simple Opacity-Transitions ist es Overkill.
Die appleEase Curve [0.16, 1, 0.3, 1] wird in jeder Datei neu definiert statt einmal zentral exportiert. Gleiche Redundanz bei spring-Konfigurationen und den tabVariants.
Im CSS gibt es .noise-overlay mit einer animierten SVG-Noise-Texture über dem gesamten Viewport. Das ist visuell schön, aber auf Mobile mit schwacher GPU ein konstanter Compositor-Hit. Ein @media (prefers-reduced-motion) deaktiviert die Animation, aber nicht das Overlay selbst — die SVG wird trotzdem gerendert.
Logging & Observability
Server-seitig wird console.log und console.error für alles verwendet. Es gibt keinen strukturierten Logger (wie pino oder winston). Im Production-Betrieb sind die Logs schwer zu parsen, filtern oder an ein Monitoring-System zu senden. Die log()-Funktion in index.ts formatiert nur den Timestamp, liefert aber kein JSON-Format.
Die Bungie-API-Calls loggen detailliert (Cache-Hits, Manifest-Größen, Postmaster-Items), aber es gibt keine Metriken: keine Request-Dauer-Histogramme, keine Error-Rate-Tracking, keine Active-Session-Counts. Für einen öffentlichen Service wäre ein /healthz-Endpoint und basic Prometheus-Metriken empfehlenswert.
Accessibility
Viele interaktive Elemente (die Slot-Picker, Item-Cards im Vault, die Charakter-Tabs) haben keine aria-label oder role-Attribute. Screenreader-Nutzer bekommen bei den meisten Buttons nur “Button” zu hören. Die destiny-clip CSS-Klassen verwenden clip-path, was bei manchen Assistive Technologies den Fokus-Ring abschneidet.
Die gesamte Farbpalette basiert auf Low-Contrast-Design (helle Grautöne auf dunklem Hintergrund). Das sieht ästhetisch aus, ist aber für Nutzer mit Sehschwäche problematisch. Ein High-Contrast-Mode oder zumindest WCAG-AA-konforme Mindestkontraste für Text wären ein guter Schritt.​​​​​​​​​​​​​​​​
