Server & Sicherheit
Das SESSION_SECRET hat einen Fallback auf 'dev-secret-change-me' — in Production sollte der Server lieber crashen, wenn das Secret fehlt, statt mit einem bekannten Default zu starten. Außerdem wird cookieParser(sessionSecret) verwendet, aber das Cookie-Signing mit signed: true funktioniert nur zuverlässig, wenn das Secret stabil bleibt. Ein Secret-Rotation-Mechanismus fehlt komplett.
Die Turnstile-Verifizierung in /api/auth/login prüft das Token, aber /api/bungie/token macht das gleiche (Token-Exchange) mit identischer Turnstile-Logik. Das ist ein doppelter Login-Endpunkt — einer davon sollte entfernt werden, sonst kann man den Turnstile-Schutz umgehen, indem man den anderen Endpunkt nutzt.
Bei insertSocketPlug wird InsertSocketPlugFree aufgerufen — das funktioniert nur für kostenlose Plug-Swaps. Wenn ein Plug Ressourcen kostet, schlägt der Call fehl, aber der Fehler wird generisch als “Insert plug failed” angezeigt. Eine spezifischere Fehlermeldung wäre hilfreich.
Performance
Das Manifest wird komplett im RAM gehalten mit allen Item-Definitionen. Bei ~50k Items ist das ein signifikanter Speicherverbrauch. Du filterst zwar nach relevanten Buckets, aber die Filterbedingung ist recht breit (alle Plugs, alle Subclass-Abilities). Ein Monitoring des Heap-Verbrauchs wäre sinnvoll.
In fetchProfileState werden die Bungie-Komponenten 100,102,103,104,200,201,202,205,206,300,302,304,305,800,900,1200,4000 alle gleichzeitig abgefragt. Das ist ein riesiger Response. Für den initialen Ladescreen bräuchte man eigentlich nur Characters + Equipment. Der Rest (Collectibles, Records, Progressions) könnte lazy nachgeladen werden — das würde die Time-to-Interactive deutlich verkürzen.
Auf Client-Seite importiert Dashboard.tsx alle Panel-Komponenten synchron. Das bedeutet der gesamte AI-Advisor-Code, News-Panel-Code etc. wird geladen, auch wenn der User nur den Hüter-Tab öffnet. Code-Splitting mit React.lazy() pro Tab würde das initiale Bundle verkleinern.
Error Handling
Die AI-Endpunkte fangen err.status === 429 ab, aber der OpenAI-Client wirft bei Rate-Limits einen Error mit err.status auf dem Error-Objekt. Wenn die AI_INTEGRATIONS_OPENAI_BASE_URL auf einen anderen Provider zeigt, könnte das Error-Format anders sein. Ein robusteres Pattern wäre, den HTTP-Status aus der Response zu extrahieren statt vom Error-Objekt.
bungieRequestWithRetry hat einen subtilen Bug: Wenn alle Retries durch Rate-Limiting erschöpft sind, wird lastError geworfen. Aber lastError ist eine BungieApiError mit errorType: 'rate_limit'. Der aufrufende Code in handleBungieError mappt das auf Status 429 — das ist korrekt. Allerdings fehlt im Client (queryClient.ts) die Rate-Limit-Erkennung in der shouldRetry-Funktion. Rate-Limited Requests werden also client-seitig nochmal 2× wiederholt, was das Problem verschlimmert.
UX-Details
Die Sprachauswahl speichert in localStorage unter forge_language — das ist vermutlich ein Überbleibsel eines alten Projektnamens. Kein Bug, aber verwirrend beim Debuggen.
Die Roll-Rating-Logik in roll-ratings.ts ist statisch und wird nicht aktualisiert. Destiny-Metas ändern sich jede Season. Eine Möglichkeit wäre, die Tier-Listen als konfigurierbare Daten auszulagern, damit sie ohne Code-Deployment aktualisiert werden können.
Beim Share-Loadout-Flow (SharePage.tsx) wird der Candidate-Matching-Score berechnet, aber es gibt keinen Hinweis, warum ein Substitute gewählt wurde. Wenn z.B. eine Fatebringer (Timelost) durch eine normale Fatebringer ersetzt wird, sieht der User nur “Substitute” — nicht, dass die Timelost-Version fehlt und die normale als bester Match gewählt wurde.
Der useOnlineStatus-Hook zeigt ein Banner bei Offline, aber die App versucht trotzdem Bungie-API-Calls. Ein Pattern wie “queue mutations while offline and replay on reconnect” wäre robuster, oder zumindest ein Deaktivieren der Action-Buttons im Offline-Zustand.
Testing & Maintainability
Es gibt data-testid-Attribute überall — das deutet auf geplante Tests hin. Aber es fehlt eine tatsächliche Testdatei im gesamten Codebase. Zumindest Integration-Tests für die Auth-Flow und die Bungie-API-Proxy-Logik wären wertvoll, besonders weil Token-Refresh ein häufiger Fehlerfall ist.
Die shared/models/chat wird in schema.ts exportiert (export * from "./models/chat"), aber diese Datei taucht nirgends im Code-Summary auf. Entweder fehlt sie im Summary oder es ist ein toter Import, der beim Build fehlschlagen könnte.​​​​​​​​​​​​​​​​
