API-Design
Der /api/bungie/profile-state-Endpunkt gibt alles in einem einzigen Response zurück — Characters, Vault, Postmaster, Currencies, Collectibles, Records, Artifact, In-Game-Loadouts. Das JSON ist vermutlich mehrere MB groß. Es gibt keinen Pagination-, Partial- oder Field-Selection-Mechanismus. Eine GraphQL-ähnliche Struktur oder zumindest Query-Parameter wie ?include=characters,vault würden Mobile-Datenverbrauch drastisch reduzieren.
Der ?fresh=true Query-Parameter auf dem Profile-Endpoint umgeht den Cache, aber es gibt keinen ETag- oder If-Modified-Since-Header. Der Client könnte mit Conditional Requests den Traffic halbieren, wenn sich seit dem letzten Poll nichts geändert hat.
Die Error-Responses sind inkonsistent: manche Endpunkte geben { message } zurück, manche { message, errorType, errorCode }, manche { success: false, message }. Ein einheitliches Error-Schema würde das Client-seitige Error-Handling vereinfachen.
Sicherheit (nochmal tiefer)
Die getClientIp-Funktion vertraut cf-connecting-ip blind. Wenn jemand direkt auf den Server zugreift (ohne Cloudflare), kann er diesen Header selbst setzen und damit Rate-Limits umgehen. Du solltest prüfen, ob der Request tatsächlich von Cloudflare kommt, bevor du diesem Header vertraust.
express.json({ limit: '1mb' }) ist recht großzügig. Die AI-Endpunkte senden Charakter-Daten, die realistisch maximal 50-100kb groß sind. Ein niedrigeres Limit pro Route wäre sicherer gegen Payload-basierte DoS.
Die CORS-Konfiguration matcht Origins mit startsWith — das bedeutet https://guardiangrid.net.evil.com würde auch durchgelassen. Ein exakter String-Match oder URL-Parsing wäre sicherer.
req.rawBody wird gesetzt aber nirgendwo verwendet. Das ist vermutlich ein Überbleibsel von einer geplanten Webhook-Verifizierung.
Typen & TypeScript
jsonb("items").$type<Record<string, any>>() in der Schema-Definition verliert jegliche Typsicherheit. Die Items in einem Loadout haben eine klar definierte Struktur (das Item-Interface), die als Zod-Schema validiert werden könnte.
Im SharePage.tsx wird loadout.items as Record<string, Item> überall gecastet. Wenn die DB-Daten korrupt sind (z.B. durch eine alte Schema-Version), gibt es keinen Runtime-Check — die Seite crasht einfach.
Die any-Types in routes.ts sind zahlreich: handleBungieError(err: any, res: any, ...), capturedJsonResponse: Record<string, any>. Das untergräbt den Zweck von TypeScript.
CSS & Rendering
Du lädst Google Fonts (Plus Jakarta Sans, Inter, Source Serif 4, JetBrains Mono, Protest Strike, Montserrat) — das sind potenziell 6 Font-Requests. Im CSS sind sie als --font-sans, --font-display etc. definiert, aber ich sehe keinen @font-face- oder <link>-Import. Entweder fehlt der Import (Fonts fallen auf System-Fonts zurück) oder er passiert in einem nicht gezeigten index.html.
Die bg-app-overlay-Klasse hat 5 überlagerte Gradients plus repeating-linear-gradients. Das sind 5 Compositing-Layers auf dem Hintergrund jeder Seite. Auf Low-End Android-Geräten kann das zu Jank beim Scrolling führen.
backdrop-filter: blur() wird extensiv verwendet (.glass, .glass-subtle, Header, Sidebar, Modals). Jede Instanz erzeugt eine separate GPU-Compositing-Layer. Bei 5+ gleichzeitigen Blur-Elementen steigt der VRAM-Verbrauch spürbar.
State Management
Der gesamte Dashboard-State (activeTab, loadout, filters, selectedCharacter, modals) lebt in useState-Hooks in einer einzigen 786-Zeilen-Komponente. Bei jedem Tab-Wechsel oder Filter-Änderung re-rendert die gesamte Dashboard-Komponente. Ein useReducer oder ein leichtgewichtiger State-Manager (Zustand) würde die Re-Renders isolieren.
Das loadout-Objekt wird in localStorage als pending_loadout gespeichert für den Share-Flow, aber es wird nie aufgeräumt, wenn der User die App verlässt, bevor es geladen wird. Stale Loadouts können monatelang im localStorage liegen.
Build & Deployment
vite.config.ts importiert Replit-spezifische Plugins (@replit/vite-plugin-runtime-error-modal, @replit/vite-plugin-cartographer). Wenn du jemals von Replit weg-deployst, müssen diese entfernt werden. Ein Environment-Check dafür fehlt beim Cartographer-Plugin (es wird nur im Dev-Mode geladen, was gut ist), aber das runtimeErrorOverlay wird immer geladen.
Es gibt kein tsconfig.json im Summary — entweder fehlt es oder es verwendet Defaults. Strikte TypeScript-Optionen wie noUncheckedIndexedAccess, exactOptionalPropertyTypes würden einige der any-Probleme auffangen.
Kein .env.example oder Dokumentation darüber welche Environment-Variablen benötigt werden. Jemand der das Projekt klont, muss den Code durchlesen um herauszufinden dass DATABASE_URL, BUNGIE_API_KEY, SESSION_SECRET, AI_INTEGRATIONS_OPENAI_API_KEY etc. nötig sind.
Destiny-spezifisch
Die GEAR_BUCKET_TO_SLOT-Mapping ist statisch. Wenn Bungie neue Slots einführt (was bei Expansions vorkommt), muss der Code manuell aktualisiert werden. Das Manifest enthält diese Bucket-Informationen — ein dynamisches Mapping wäre zukunftssicherer.
Die CLASS_NAMES-Map hat nur 3 Einträge (Titan, Hunter, Warlock). classType: 3 bedeutet in der Bungie-API “alle Klassen” (für klassenunabhängige Items), wird aber nirgends explizit behandelt.
In-Game-Loadouts werden über Komponente 1200 abgerufen, mit einem Fallback-Request wenn sie im Haupt-Call fehlen. Dieser Fallback ist gut, aber er loggt nur — es gibt keinen User-sichtbaren Hinweis, dass In-Game-Loadouts nicht verfügbar sind. Der User sieht einfach einen leeren Tab.
